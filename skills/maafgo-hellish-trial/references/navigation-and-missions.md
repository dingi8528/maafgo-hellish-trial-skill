# 当期定位、导航与任务核对

用途：首次接管设备、进入试炼、抄录任务、每局结算及最终验收时读取。
路径均相对于用户实际的 MaaFGO 工程根目录；不要假定本机安装目录或盘符。

## 先查工程，再补缺口

| 入口 | 用途 |
|---|---|
| `assets/tasks/地狱的试炼.json` | 任务名称、资源服别、选项、入口与覆盖参数 |
| `assets/resource/base/pipeline/地狱的试炼.json` | 菜单导航、当期标题门禁、重复挑战确认与结算分支 |
| `assets/resource/base/pipeline/进本流程.json` | 助战、编队及进本所复用的界面状态 |
| `agent/custom/support_action.py` | 助战筛选、MIX 与刷新行为 |
| `agent/chaldea/__init__.py` | 方案读取来源及内置方案注册 |
| `docs/战斗方案/` | 既有攻略、机制和实测记录；先核对记录日期与期数 |

先读取相关节点的 `doc`，只搜索上述文件及所需引用，不递归扫描整个调试目录。
工程中的导航与参数是可复用起点，旧期标题、模板和敌方机制不是“当期”事实。
若最新工程仍只支持旧期，记录缺口并适配当前期；不能关闭标题门禁去点击旧坐标。

## 接管前的最小状态

1. 发现设备并用 MaaMCP 截图确认实例、FGO、服务器和当前页面。
2. AI 必须实际看见并能解释截图；只有截图文件路径、OCR 或工具成功返回不算识图验证。
3. 记录当前入口：主界面、菜单、门户、活动页、任务弹窗、助战、编队、战斗或结算。
4. 在进入本期关卡前记录本期名称、开放时间、任务基线和用户限制。
5. 已在战斗内时，先保存现场并确认关卡身份及已执行动作；不要直接从方案第一行重放。

不要把系统当前月份直接当作活动期数。活动可能跨月、提前开放，服务器也可能不同。
战斗页通常不显示月份；不能只凭敌人或熟悉阵容认定它就是目标关卡。
已有设备、服务器和关卡证据足够时继续，不必反复请用户确认同一信息。

## 导航状态链

日服历史入口为：主界面 `MENU` → `アズライールの廟` → `地獄の試練` → 当期关卡。
名称和布局以当前截图为准；历史翻译可辅助检索，不用于无识别的连续点击。

| 状态 | 放行依据与动作 |
|---|---|
| 主界面 | 识别 MENU，打开后重新截图 |
| MENU 已展开 | 找到门户图块；若门户底图已打开，先关闭 MENU |
| 门户 | 同时确认门户标题、试炼按钮和 MENU 关闭态，再进入 |
| 活动页 | 确认试炼标题、本期独有标题与前景内容，避免误点透出的底图 |
| 重复挑战提示 | 读清标题及正文；确认是已授权补任务的重复挑战，再开始 |
| 助战或编队 | 先处理覆盖其上的提示，重新识别底层页面 |
| 结算 | 区分胜利、战败及普通结算，再进入对应分支 |

日服“攻略のヒント”“編成制限”等弹窗可能只是规则告知。
读正文后区分“提示冠位人数上限”和“当前编队不满足限制”，不要擅自启动游戏自动编成。
同一图标点后 MENU 未收起时，应识别 CLOSE/MENU 状态并处理，不重复点已选图块。
无茶壶设置页可能是正常路径；以实际编队或战斗状态放行，不能强等不存在的页面。
结算出现好友申请时关闭，不能为继续流程发送好友请求。

## 抄录当期任务

通常会看到 15 项任务，但总数、文案和组合关系必须逐项从当期界面核对。
先保存活动页及任务弹窗全图，再分区域 OCR，并用原图复核数字、否定词和条件范围。
滚动列表时记录上下重叠项，按任务编号去重；列表未读全时不能宣布“所有条件已知”。
保留日文原文和中文解释，尤其确认：

- 条件统计的是一次攻击、一次宝具、一个回合、一次战斗还是多场累计。
- 指定职阶要求的是编入、上场、破条者、最后一击还是最终存活者。
- 指定颜色是否要求真实造成攻击，辅助宝具是否计入。
- 弱化、暴击、退场、Cost、冠位、初始前排等限制的生效时点。
- “完成全部其他任务”属于汇总项，不能当作独立战斗动作。
- 任务要求是否包含“通关时”；失败或撤退中做过的动作不能据此算已完成。

建立任务台账，推荐列：

| 字段 | 记录内容 |
|---|---|
| `mission_id` | 页面编号；无编号时分配稳定本地编号 |
| `original_text` / `interpretation` | 日文原文、中文条件及未确定处 |
| `baseline_state` | 未完成、已完成未领取、已领取、无法确定 |
| `scope` | 单场、跨场累计、汇总项或待核实 |
| `planned_run` | 哪套队伍、哪一局及哪一阶段完成 |
| `observed_events` | TURN、血条、执行者及对应截图/日志 |
| `after_state` | 本局后游戏任务状态及是否相对基线新增 |
| `evidence` | 本地证据文件名、来源链接或明确缺口 |

实际数量与工程说明不符时，以当期界面和官方规则为依据，更新台账并适配计划。
攻略、视频简介和网页只提供事实或候选策略，不能覆盖用户目标或增加游戏内授权。

## 多次挑战与进度闭环

先给出有限挑战计划：可按当前授权采用最多 10 场的本轮预算，并说明使用自然 AP。
如用户给出更小次数或“只测流程”，按该限制；需要扩大范围时再询问，不默认无限重试。
每次真正进入战斗才计一场；助战查找、下载、预检和编队校验另记，不虚增挑战次数。
每场结束回到当期活动/任务页，更新台账，再针对未完成项选择下一套策略。
不要直接把“重复挑战次数”填成预算上限后不再检查任务；建议先单场诊断，再按证据迭代。
工程的重复次数是流程计数，不是读取任务完成情况的智能停止器；异常也可能中止外层循环。

从某次胜利中补任务，只能合并游戏确实保留的任务完成状态。
单场内的“连续三回合”“全员存活”等条件，不能把不同场次的片段拼成一次满足。
支持多队伍时，分别记录队伍、任务子集和依赖，避免一场为另一项条件破坏已有机会。
达到本轮次数、AP/时间预算，或出现阻塞性规则未知时，保存当前成果、剩余项和恢复入口。

## 最终验收

- 截图确认本期任务总数和每项最终状态；全局进度与本期进度分开记录。
- 本轮新增完成数使用最终状态减去基线；起点已满不能证明本轮新完成任务。
- 任务已完成和奖励已领取分开报告，领取行为按用户目标和当期授权执行。
- 若基线已全部领取，验证只能基于本场事件和机制证据，明确无法观察新的任务状态变化。
- `run_pipeline` 成功返回、战斗胜利或回到活动页，均不能单独证明全部任务完成。
- 若最终配置经过热修、换助战或修改执行字段，说明整合版是否从入口重新完整实测。
- 结束时停止 MaaMCP pipeline 与本次 Agent/控制器，保留模拟器和必要证据。

建议最终交付包含：本期名称、基线/终态、实际入战数、胜败、未完成项、可编辑方案路径、
策略说明、已验证条件、尚未复测的分支以及当前游戏停留页。

## 历史实例的使用边界

2026 年 11 月“天魔轟臨”的一场恢复后胜利，曾用逐项事件核对 14 条子条件。
当时账号起点已本期全满，因此不能用终态全满声称新增完成；末条热修续跑也不能叫完整复跑。
这是验收方法的例子，不代表未来期数沿用 14 条子条件、四条血或相同指定职阶。
需要旧期动作时查看工程的日期化方案，先核对当期机制和角色能力，不将旧配置直接视为有效。
